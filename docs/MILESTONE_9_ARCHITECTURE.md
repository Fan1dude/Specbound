## Storage subsystem — complete

Findings **S1**, **S3**, and **S6** below (§4 Security) drove a full, separately-tracked remediation effort — three migrations (`0017_storage_rls_hardening` / Migration A, a client-side legacy-URL compatibility layer / Migration B, `0018_legacy_media_linkage_backfill` / Migration C) — all applied, live-verified, and closed out:

- **S1** (bucket public/private flag unverified, potential Critical exposure): **resolved**. Live check found the bucket was in fact still Public, *and* found 4 additional untracked, overly-broad `storage.objects` policies beyond what any migration ever created (worse than S1 alone anticipated — including an anonymous-role INSERT policy). All 4 broad policies dropped, 2 correctly-scoped avatar policies added, bucket flipped to Private, full regression suite passed (uploads, reads, listing, cross-user isolation), all reconfirmed live.
- **S3** (avatar-upload storage policy unverifiable from disk): **resolved** as part of the same fix — the 2 new policies added by Migration A (`"Owners can upload their own avatar files"`, `"Owners can update their own avatar files"`) are now tracked, scoped exactly to `avatars/{auth.uid()}/*`.
- **S6** (`uploadGalleryImage()` still constructs a discarded public URL): **still present, unchanged** — re-verified 2026-07-26, `js/services/imageService.js:129-134` still calls `getPublicUrl()` and returns it, still unused by its only caller. Rolled into Phase 9C (production cleanup) rather than fixed as part of the storage remediation, since it was always a no-op dead-output cleanup item, not a security gap (the bucket being private means the returned URL never worked anyway).
- Two further legacy-data problems, discovered only once S1 was being fixed (not originally in this document), were also resolved: pre-Milestone-5A **full public URLs** stored in `image_url`/`avatar_url` columns (Migration B, read-path-only compatibility layer, no data rewritten) and **pre-`revision_media`-tracking legacy images** that the tightened RLS made unreadable even to their own owner (Migration C, a scoped 7-row backfill with a documented, unbackfilled "Verified Legacy Covers" exception set).

Full detail — bucket structure, folder layout, upload/read flows, the compatibility layer, Category A/B backfill rules, orphan handling, and the complete migration list — is now documented in **[`docs/STORAGE_ARCHITECTURE.md`](STORAGE_ARCHITECTURE.md)**, the authoritative reference for this subsystem going forward. This document's §4 Security table below is left as originally written (historical record of what was found), with S1/S3 individually annotated `RESOLVED`.

**Security score note**: §"Production Readiness Scores" below still shows the original pre-fix 6/10 for Security, scored honestly against the state *at audit time*. It is not retroactively edited here since the numeric table is a snapshot, not a live tracker — the storage-driven blockers within it (S1, S3) are now closed, and Phase 9E (final launch verification) is where the score gets formally recomputed against the then-current state, folding in whatever Phase 9C/9D work has also landed by that point.

## Executive summary

**Bottom line: not launch-ready today.** Nothing found is architecturally hard to fix, but there are 3 genuinely **Critical/High security unknowns** that cannot be resolved by reading code — they require a live Supabase dashboard check — plus **no version control, no deployment pipeline, and no rollback plan** at all. Those four things alone mean a "publish now" launch would be irresponsible regardless of how clean the application code is.

- **68 findings total** across 6 categories: 1 Critical (pending live confirmation), 4 High, ~20 Medium, ~40 Low.
- **The single most important thing to resolve first**: confirm whether the `project-images` Storage bucket is still flagged *public* at the bucket-config level. This setting lives outside every migration file — `migrations.md` explicitly deferred flipping it and no later migration ever did. If it's still public, the entire "private bucket, signed URLs only" model this app's comments describe throughout the codebase provides **no actual confidentiality**, regardless of how correct the RLS policies are.
- **Two more unverifiable-from-code items** (`profiles` table RLS, the avatar-upload storage policy) predate migration tracking entirely and need the same live check.
- Everything that **can** be verified from code is in strong shape: all 14 RPC functions correctly use `SECURITY DEFINER` with internal `auth.uid()` checks and zero caller-supplied-identity parameters (re-confirmed across all 16 migrations, no regressions since the 8A checkpoint); zero broken imports; zero secrets in the repo; zero `TODO`/`FIXME` markers anywhere.
- Dead code has a real recurrence problem: **`css/layout/grid.css` and `css/themes/light.css` are entirely dead despite being actively imported** — the same "imported but fully unused" bug class that 8D's cleanup pass was specifically meant to close out. This suggests the codebase needs a mechanical way to catch this (a simple "grep every class name" script), not just periodic manual passes.
- The escaping-utility consolidation started in 8D was left half-finished: only 2 of ~20 files were migrated to the new shared `js/utils/escapeHtml.js`.
- I found and independently verified two literally-empty asset files that were previously assumed fine: `favicon.svg` and `default-cover.svg` are both **0 bytes** — 8D confirmed the favicon *link* resolves with HTTP 200, but never checked the file actually contains an icon. Every browser tab currently shows a blank icon, and every image-less build card renders a blank placeholder instead of a visible "no image" graphic.
